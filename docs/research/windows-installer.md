# Windows installer and auto-update options for SyncThis (Electron + Forge)

Retrieved: 2026-10-01. Sources are primary (Electron Forge docs/source, electron/electron docs, update.electronjs.org source, Squirrel.Windows repo, electron-builder docs, actions/runner-images). Docs are "latest" unless a version is noted. Recommendation-neutral; no option is picked.

Context from this repo (read-only): Forge `packagerConfig` has `asar: { unpack: '**/dugite/git/**' }`, `extraResource: ['resources/tray', '../cli/dist']`, fuses `EnableEmbeddedAsarIntegrityValidation` and `OnlyLoadAppFromAsar` on (`packages/gui/forge.config.ts`). The release workflow is a matrix of `macos-latest` and `ubuntu-latest`, Node 20, and uploads only `*.dmg|*.deb|*.zip` with a `gh release upload` loop (`.github/workflows/gui-release.yml`). `packages/gui/src/main/updater.ts` uses `autoUpdater` + `https://update.electronjs.org/mischah/syncthis/${process.platform}-${process.arch}/${version}` on macOS only and GitHub API polling otherwise.

## 1. maker-squirrel

- **Outputs:** Setup.exe, `-full.nupkg`, `RELEASES` ([Forge](https://www.electronforge.io/config/makers/squirrel.windows)). Source adds a delta nupkg only if `remoteReleases` is set and `noDelta` is not, and an MSI unless `noMsi` ([MakerSquirrel.ts](https://raw.githubusercontent.com/electron/forge/main/packages/maker/squirrel/src/MakerSquirrel.ts)). Output dir includes arch: `squirrel.windows/<arch>` (same file).
- **Install location:** `%LocalAppData%\<App>`, with a `packages` folder and per-version `app-1.0.0`, `app-1.0.1` folders ([install-process](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/install-process.md)).
- **Admin:** "no-prompt, no-hassle, no-admin" ([Forge](https://www.electronforge.io/config/makers/squirrel.windows)); "no UAC dialogs, does not require reboot" ([README](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/README.md)).
- **Shortcuts:** shortcuts point to `Update.exe --processStart <App>.exe` ([install-process](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/install-process.md)). `electron-squirrel-startup` creates/removes them via `Update.exe --createShortcut/--removeShortcut` on `--squirrel-install`/`--squirrel-updated`/`--squirrel-uninstall` ([source](https://raw.githubusercontent.com/mongodb-js/electron-squirrel-startup/master/index.js)). Shortcut AUMID is `com.squirrel.PACKAGE_ID.YOUR_EXE_WITHOUT_DOT_EXE`; match it with `app.setAppUserModelId` ([autoUpdater](https://raw.githubusercontent.com/electron/electron/main/docs/api/auto-updater.md)).
- **Uninstall:** `--squirrel-uninstall` is passed to the app, which should exit quickly ([squirrel events doc](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/custom-squirrel-events-non-cs.md)). The Add/Remove Programs entry is not documented in the pages fetched (see Unverified).
- **Limitations:** Setup.exe customisation is limited to options such as `setupIcon` and `loadingGif` ([electron-winstaller](https://raw.githubusercontent.com/electron/windows-installer/main/README.md)); no wizard ("Wizard-Free", [README](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/README.md)). Machine-wide installs are a separate Group Policy MSI flow ([machine-wide-installs](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/machine-wide-installs.md)). `electron-winstaller` requires 64-bit Node and "Node.js 22.12+" ([README](https://raw.githubusercontent.com/electron/windows-installer/main/README.md)); the workflow here uses Node 20. Config `authors`/`description` are required; the Forge config field is `authors`, package.json uses `author` ([Forge](https://www.electronforge.io/config/makers/squirrel.windows)).
- **Names with spaces / hyphens:** Forge docs prescribe hyphenated package `name`, spaced `productName`, camelCase maker `name`, plus `app.setAppUserModelId()` ([Forge](https://www.electronforge.io/config/makers/squirrel.windows)). Source replaces `-` with `_` in the Squirrel id ("squirrel hates hyphens") ([MakerSquirrel.ts](https://raw.githubusercontent.com/electron/forge/main/packages/maker/squirrel/src/MakerSquirrel.ts)).
- **Required startup handling:** Squirrel launches the app with `--squirrel-install`, `--squirrel-firstrun`, `--squirrel-updated`, `--squirrel-obsolete`, `--squirrel-uninstall` (each with a version). Exit promptly on all but firstrun, which should run normally ([events doc](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/custom-squirrel-events-non-cs.md)). `electron-squirrel-startup` handles install/updated/uninstall/obsolete and is meant to be called first in main ([README](https://raw.githubusercontent.com/mongodb-js/electron-squirrel-startup/master/README.md)). `update-electron-app` says extra app launches on Windows indicate unhandled Squirrel events ([README](https://raw.githubusercontent.com/electron/update-electron-app/main/README.md)). On `--squirrel-firstrun` Squirrel holds a file lock, so update checks fail; skip checks or wait about 10 seconds ([autoUpdater](https://raw.githubusercontent.com/electron/electron/main/docs/api/auto-updater.md)). A known 15-second limit on post-install actions is reported in [Squirrel issue #501](https://github.com/Squirrel/Squirrel.Windows/issues/501) (search-result snippet only; see Unverified). Note: this repo's main process would also need to avoid its tray/git startup work during these events (design implication, not a sourced claim).

## 2. maker-wix (MSI)

- **Output:** `.msi` ([Forge](https://www.electronforge.io/config/makers/wix-msi)). Needs WiX Toolset v3; Forge example pins `choco install wixtoolset --version=3.14.0` (same). README names `light` and `candle` ([maker README](https://raw.githubusercontent.com/electron/forge/main/packages/maker/wix/README.md)). Config requires `language` and `manufacturer` (Forge page).
- **Windows only:** `isSupportedOnCurrentPlatform` returns `process.platform === 'win32'`; arches `x64 | ia64 | x86` ([MakerWix.ts](https://raw.githubusercontent.com/electron/forge/main/packages/maker/wix/src/MakerWix.ts)).
- **Scope:** underlying `electron-wix-msi` defaults `defaultInstallMode` to `perMachine`, installs to Program Files / Program Files 64, with a per-user mode available ([creator.ts](https://raw.githubusercontent.com/felixrieseberg/electron-wix-msi/master/src/creator.ts)). It supports up- and downgrades and uses a version-based folder structure ([README](https://raw.githubusercontent.com/felixrieseberg/electron-wix-msi/master/README.md)).
- **autoUpdater:** Electron's `autoUpdater` on Windows selects MSIX or Squirrel.Windows only ([autoUpdater](https://raw.githubusercontent.com/electron/electron/main/docs/api/auto-updater.md)); the page does not mention MSI. `electron-wix-msi` can embed Squirrel's updater (`msq.exe`) when the `autoUpdate` feature is enabled; off by default ([creator.ts](https://raw.githubusercontent.com/felixrieseberg/electron-wix-msi/master/src/creator.ts)). This is a separate mechanism from update.electronjs.org's RELEASES flow (inference).
- **Version mangling:** MSI uses `major.minor.build.revision`; semver prerelease is not retained ([MakerWix.ts](https://raw.githubusercontent.com/electron/forge/main/packages/maker/wix/src/MakerWix.ts)).
- **GitHub Actions:** the Windows Server 2025 image (`windows-latest`, per [runner-images README](https://raw.githubusercontent.com/actions/runner-images/main/README.md)) lists WiX Toolset 3.14.1.8722, Visual Studio 2022 17.14, Windows SDK 10.0.26100, Node 22.23.2/24.21.0, Chocolatey 2.7.4; no Wine/Mono (image version 20260922.270.2, [Windows2025-Readme](https://raw.githubusercontent.com/actions/runner-images/main/images/windows/Windows2025-Readme.md)). The README warns `-latest` migrates gradually and suggests pinning (e.g. `windows-2022`).

## 3. NSIS and other makers

- **Official Forge makers named in docs index:** appx, msix, squirrel.windows, wix-msi, zip (Windows-relevant) ([llms.txt](https://www.electronforge.io/llms.txt)). No NSIS maker in that index.
- **Forge maintainers on NSIS:** issue [#3069](https://github.com/electron/forge/issues/3069) closed "not planned"; maintainer comment (via [API](https://api.github.com/repos/electron/forge/issues/3069/comments)): "I don't see NSIS on our immediate plans, a community maker for NSIS is very possible, our next potential target for windows is probably MSIX."
- **electron-builder coexistence:** electron-builder ships `electron-forge-maker-nsis` and `electron-forge-maker-nsis-web`; each "is a thin wrapper around `buildForge()` from `app-builder-lib`", configured via the maker `config`, e.g. `new MakerNsis({ oneClick: false })`. Publishing, Auto Update and Code Signing "are unavailable through Forge makers" ([electron-builder docs](https://www.electron.build/docs/features/electron-forge/)). Forge's own docs frame electron-builder as an alternative with a different philosophy ([why-electron-forge](https://www.electronforge.io/core-concepts/why-electron-forge)).
- **NSIS options:** `oneClick` default true; `perMachine` default false; assisted installer shows install-mode page when `perMachine` is false; default artifact name `${productName} Setup ${version}.${ext}`; `differentialPackage` option ([nsis docs](https://www.electron.build/docs/nsis/)). electron-builder's default Windows target is NSIS; `msi`, `msi-wrapped`, `squirrel`, `portable`, `appx`, `msix` also exist ([win docs](https://www.electron.build/docs/win/)).
- **maker-zip:** cross-platform; the RELEASES.json manifest is macOS-only ([zip maker](https://www.electronforge.io/config/makers/zip)).
- **MSIX:** needs Windows 10/11 + Windows SDK; signing via `windowsSignOptions` (uses `@electron/windows-sign`); experimental as of Forge v7.10 ([msix](https://www.electronforge.io/config/makers/msix.md)). Electron's MSIX updater supports `.msix` direct link or JSON feed, `allowAnyVersion` for downgrades ([autoUpdater](https://raw.githubusercontent.com/electron/electron/main/docs/api/auto-updater.md)). This app is on Electron 33; update.electronjs.org MSIX needs Electron 41+ ([README](https://raw.githubusercontent.com/electron/update.electronjs.org/main/README.md)).
- **AppX:** Windows 10/11 + SDK; targets the Microsoft Store ([appx](https://www.electronforge.io/config/makers/appx.md)).

## 4. Auto-update

- **Built-in support:** `autoUpdater` supports macOS and Windows, not Linux; on Windows it picks MSIX or Squirrel.Windows automatically ([autoUpdater](https://raw.githubusercontent.com/electron/electron/main/docs/api/auto-updater.md)). Windows Squirrel updates read `RELEASES`; the server must return the latest `RELEASES` and "should return a response even when no update is available" ([Updating Apps](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/updates.md)).
- **update.electronjs.org requirements:** macOS or Windows, public GitHub repo, builds on GitHub Releases, "code signed (macOS and MSIX only)". URL forms include `/:owner/:repo/:platform-:arch/:version` ([README](https://raw.githubusercontent.com/electron/update.electronjs.org/main/README.md)). Windows `platform` is `win32`, arches `x64|ia32|arm64` (same). The app's existing `${process.platform}-${process.arch}` URL therefore yields `win32-x64` on Windows (inference from the README table plus `updater.ts`).
- **Release filtering (source):** skips releases that fail `semver.valid(tag_name)` or are `draft` or `prerelease`; keeps the first matching asset per platform ([updates.ts](https://raw.githubusercontent.com/electron/update.electronjs.org/main/src/updates.ts)).
- **Windows asset detection (source):** `assetPlatform` matches `-win32-(ia32|x64|arm64)` anywhere in the file name; arch from `-ia32`/`-arm64`, else x64. Fallback: any `.exe` without `arm`/`ia32` is treated as win x64. `.msix` needs `-win32-(x64|arm64)` ([asset-platform.ts](https://raw.githubusercontent.com/electron/update.electronjs.org/main/src/asset-platform.ts)). For comparison, the macOS rule needs `.zip` with `mac|darwin|osx` (same file).
- **RELEASES retrieval (source):** for each Windows platform with a matched asset, the service fetches `https://github.com/<owner>/<repo>/releases/download/<tag>/RELEASES`, reads the nupkg name from its contents, and rewrites it to a full URL in the same release ([updates.ts](https://raw.githubusercontent.com/electron/update.electronjs.org/main/src/updates.ts)). So the release must carry an asset literally named `RELEASES` and the nupkg.
- **update-electron-app:** states every GitHub Release needs the `RELEASES` manifest, full/delta `.nupkg`, and `.exe` installer ([README](https://raw.githubusercontent.com/electron/update-electron-app/main/README.md)).
- **Signing for unsigned Windows apps:** the Electron docs and update.electronjs.org list signing as macOS-only (and MSIX) for the service ([Updating Apps](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/updates.md)). The Squirrel docs "do not explicitly state whether signing is required for updates", only that it avoids SmartScreen/AV warnings ([application-signing](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/application-signing.md)). Electron's code-signing tutorial: unsigned apps are not blocked outright but users must "go through multiple advanced and manual steps"; SmartScreen warnings apply ([code-signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)). Forge's Windows signing guide says signing happens at the installer level during Make, using a `.pfx` and `certificateFile`/`certificatePassword`, and mentions Azure Trusted Signing ([guide](https://www.electronforge.io/guides/code-signing/code-signing-windows.md)).
- **If autoUpdater is unusable (MSI/NSIS):** options documented: electron-builder `electron-updater` (full publish pipeline, not via Forge makers; [docs](https://www.electron.build/docs/features/electron-forge/)); the current repo pattern of polling GitHub Releases and opening the release page (existing `startLinuxUpdater`); `electron-wix-msi`'s bundled Squirrel updater option. Static storage feeds are supported by `update-electron-app` for Squirrel ([README](https://raw.githubusercontent.com/electron/update-electron-app/main/README.md)).

## 5. Building on GitHub Actions

- Forge Squirrel/WiX/MSIX makers all run on Windows hosts; WiX v3 and the Windows SDK are preinstalled on the Windows Server 2025 image (see section 2). electron-winstaller needs 64-bit Node, 22.12+ ([README](https://raw.githubusercontent.com/electron/windows-installer/main/README.md)). Not verified: .NET Framework requirement for Squirrel builds (see Unverified).
- Squirrel on Linux/macOS: Forge docs say "Linux machine with Mono and Wine installed"; `electron-winstaller` throws without both Mono and Wine on non-Windows ([Forge](https://www.electronforge.io/config/makers/squirrel.windows), [electron-winstaller src](https://raw.githubusercontent.com/electron/windows-installer/main/src/index.ts)). The Windows Server 2025 image lists neither ([Windows2025-Readme](https://raw.githubusercontent.com/actions/runner-images/main/images/windows/Windows2025-Readme.md)). Not recommended or evaluated here.
- Forge's GitHub publisher uploads every artifact via `path.basename` ([source](https://raw.githubusercontent.com/electron/forge/main/packages/publisher/github/src/PublisherGitHub.ts)); this repo does not use it and instead uploads by file extension (`gui-release.yml`), so `.exe`, `.nupkg` and extension-less `RELEASES` would not be uploaded without changing that filter (repo observation).

## 6. asar, fuses, extraResource on Windows

- **Asar integrity on Windows:** supported "as of `electron>=30.0.0`" (macOS 16+). Requires the `EnableEmbeddedAsarIntegrityValidation` fuse; `onlyLoadAppFromAsar` recommended. Windows stores an `Integrity` resource `ElectronAsar` in the exe. Forge/Packager do this automatically when `asar` is enabled, with min `@electron/packager@18.3.1` and Forge 7.4.0 ([asar-integrity](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/asar-integrity.md)). Repo is Electron 33.2.0 and Forge 7.11.1, within those bounds. The fuse description covers macOS and Windows ([fuses](https://www.electronjs.org/docs/latest/tutorial/fuses)).
- **Unpacked files:** `--unpack` creates `app.asar.unpacked`; `execFile` works on asar binaries but `exec`/`spawn` do not ([asar-archives](https://www.electronjs.org/docs/latest/tutorial/asar-archives)). Whether unpacked dugite git binaries on Windows interact with integrity, signing, or antivirus is not documented in sources fetched (see Unverified).
- **extraResource:** copied into `resources` for non-macOS targets, readable via `process.resourcesPath` ([packager Options](https://electron.github.io/packager/main/interfaces/Options.html)). In a Squirrel install this should resolve to `%LocalAppData%\<App>\app-<ver>\resources\` (derived from the packager and install-process docs; the exact path was not shown in a primary source). MSI layout: not verified.
- **Fuses plugin:** `FusesPlugin` takes the same arguments as `flipFuses` ([plugin doc](https://www.electronforge.io/config/plugins/fuses)).
- **Asar and build time:** a maintainer notes disabling ASAR caused 25-minute Windows builds and recommends enabling ASAR ([#3069 comments](https://api.github.com/repos/electron/forge/issues/3069/comments)).

## 7. Artifact naming

- **Squirrel (source):** Setup.exe defaults to `${appName}-${version} Setup.exe` in the Forge maker; electron-winstaller otherwise `${productName}Setup.exe`, configurable via `setupExe`; MSI `${productName}Setup.msi`, configurable via `setupMsi`; full nupkg `${name}-${version}-full.nupkg`; `RELEASES` fixed ([MakerSquirrel.ts](https://raw.githubusercontent.com/electron/forge/main/packages/maker/squirrel/src/MakerSquirrel.ts), [electron-winstaller src](https://raw.githubusercontent.com/electron/windows-installer/main/src/index.ts)). The repo's `postMake` hook pattern (renaming `.deb`) can mutate `result.artifacts`; the same hook could rename the Setup.exe but the nupkg name is referenced inside `RELEASES`, so it should not be renamed (reasoning from the RELEASES rewrite in [updates.ts](https://raw.githubusercontent.com/electron/update.electronjs.org/main/src/updates.ts)).
- **For update.electronjs.org:** the Setup.exe must be matchable: either contain `-win32-x64` (e.g. `SyncThis-<ver>-win32-x64-setup.exe`) or be an `.exe` without `arm`/`ia32` (fallback, would be classed x64). The `RELEASES` and nupkg are matched only via the RELEASES file, not by name rules ([asset-platform.ts](https://raw.githubusercontent.com/electron/update.electronjs.org/main/src/asset-platform.ts), [updates.ts](https://raw.githubusercontent.com/electron/update.electronjs.org/main/src/updates.ts)).
- **WiX:** output name controlled by MSICreator options (not enumerated in sources fetched). **NSIS:** `artifactName` option ([nsis docs](https://www.electron.build/docs/nsis/)).
