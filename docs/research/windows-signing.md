# Windows code signing options for SyncThis (Electron + Forge, individual maintainer in Australia)

Retrieved: 2026-10-01. Every price and eligibility claim below was read from the vendor's page on that date; prices and eligibility change often. Sources are primary (Microsoft Learn/Azure, SignPath Foundation, CA vendor pages, Electron/Forge/@electron/windows-sign/electron-winstaller/Squirrel docs, GitHub docs). Recommendation-neutral; no option is picked. No code was changed.

Context: Electron 33.2.0, Forge 7.11.1, releases built in GitHub Actions; see [windows-installer.md](./windows-installer.md) for the maker comparison.

## 1. Microsoft Artifact Signing (formerly Trusted Signing)

- **Availability and regions:** Accounts can be created in 15 listed Azure regions (e.g. East US, West Europe, Japan East, Korea Central; no Australian region) ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)). The Australia-based user can still pick a US/EU region; endpoint must match the account region (same page, [integrations](https://learn.microsoft.com/en-us/azure/artifact-signing/how-to-signing-integrations)).
- **Eligibility:** "Public Trust certificates are available to organizations in the United States, Canada, the European Union, the United Kingdom, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel. Individual developers must be located in the United States or Canada." ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)). So an Australian **organisation** is eligible and an Australian **individual** is not. Individual validation also needs an Azure billing account of type Individual whose legal name and address match a government ID (same page).
- **Identity validation:** Organisation: legal entity name, website, a monitored email on the entity's domain, a business identifier, address, plus individual ID validation of the representative; takes 1 to 20 business days, three document attempts ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart), [FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)). Individual: Microsoft Authenticator Verified ID via AU10TIX with government ID and face check (same). Certificate CN/O cannot be customised ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)).
- **Subscription:** a paid Azure subscription is required; free, trial or sponsored subscriptions are not supported ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)).
- **Price:** see table. Billing starts at account creation, full SKU amount, not pro-rated ([Azure pricing](https://azure.microsoft.com/en-au/pricing/details/artifact-signing/), [FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)). Per-signature overage price is not displayed on the pricing page when fetched.
- **No EV:** "Artifact Signing doesn't issue Extended Validation (EV) certificates" with no plan to ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)). HSM compliance FIPS 140-3 Level 3 (same). All file types SignTool supports can be signed (same).
- **GitHub Actions:** `azure/artifact-signing-action@v2` with `endpoint`, `signing-account-name`, `certificate-profile-name`, `files`/`files-folder`/`files-folder-filter`, `file-digest`, `timestamp-rfc3161`; Windows runners only (windows-2022/2025); OIDC via `azure/login@v3` recommended ([action README](https://github.com/Azure/artifact-signing-action)). OIDC setup: federated credential, `id-token: write`, `azure/login` ([GitHub docs](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-azure)). Role needed: Artifact Signing Certificate Profile Signer ([integrations](https://learn.microsoft.com/en-us/azure/artifact-signing/how-to-signing-integrations)).
- **signtool + dlib:** requires Windows SDK SignTool 10.0.2261.755+ (the 20348 SDK is unsupported), .NET 8 runtime, VC++ redistributable, `Microsoft.ArtifactSigning.Client` dlib and a `metadata.json`; command `signtool sign /v /debug /fd SHA256 /tr http://timestamp.acs.microsoft.com /td SHA256 /dlib <dlib> /dmdf <metadata.json> <file>` ([integrations](https://learn.microsoft.com/en-us/azure/artifact-signing/how-to-signing-integrations)).
- **Forge / @electron/windows-sign:** Forge's guide shows `windowsSign` with `signWithParams: /v /debug /dlib ... /dmdf ...`, `timestampServer: http://timestamp.acs.microsoft.com`, set in both `packagerConfig.windowsSign` and the Squirrel maker, with `AZURE_CLIENT_ID/SECRET/TENANT_ID` env vars ([Forge guide](https://www.electronforge.io/guides/code-signing/code-signing-windows)). The guide still uses the "Trusted Signing" name. `@electron/windows-sign` bundles a signtool from Windows SDK 10.0.26100.9169, which meets the dlib minimum ([README](https://raw.githubusercontent.com/electron/windows-sign/main/README.md)). Electron says the service "is currently limited to developers in certain countries" and also lists `jsign` for non-Windows hosts ([Electron code signing](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/code-signing.md)).

## 2. SignPath Foundation (free for open source)

- **Criteria:** OSI-approved licence "without commercial dual-licensing", no proprietary components (system libraries aside), actively maintained, already released in the form to be signed, functionality described on a download page, no malware/PUP ([terms](https://signpath.org/terms.html)).
- **Team rules:** Authors, Reviewers (review each external contribution) and Approvers (approve every signing request); MFA for SignPath and the repo; sign only your own binaries; binaries must come from verifiable automated builds with metadata attributes enforced; every release needs manual approval; publish a "Code signing policy" page crediting SignPath Foundation; privacy policy if collecting data; uninstall support required ([terms](https://signpath.org/terms.html)). The Foundation may pause subscriptions or revoke certificates without notice (same).
- **Individual applicants:** the terms page describes team roles but neither permits nor forbids a one-person team; the [homepage](https://signpath.org/) says certificates are tied to the repository rather than a personal identity. Whether a sole maintainer can fill Author, Reviewer and Approver roles is not stated (see Unverified). The `/apply` page returned only a heading when fetched, so process, timeline and country restrictions were not read.
- **Is the fork eligible?** The "must be your own project" rule and "Modified upstream forks require the original project to publish signed builds" ([terms](https://signpath.org/terms.html)) are directly relevant to a public fork of mischah/syncthis. Whether this fork qualifies is not stated; needs asking SignPath.
- **CI:** supported trusted build systems: Jenkins, GitHub, GitLab, Azure DevOps, TeamCity, AppVeyor; trusted build system is required for open-source signing ([docs](https://docs.signpath.io/trusted-build-systems)). For OSS, "all jobs of the GitHub workflow leading up to the signing request were executed on GitHub-hosted agents" ([GitHub integration](https://docs.signpath.io/trusted-build-systems/github)). Origin verification checks repo URL, branch, commit, build job URL and reproducibility; build scripts and CI config must be in review scope ([origin verification](https://docs.signpath.io/origin-verification/)).
- **Integration:** `actions/upload-artifact@v7` then `signpath/github-action-submit-signing-request@v3` with `api-token`, `organization-id`, `project-slug`; upload-artifact produces a ZIP so the artifact configuration's root must be `<zip-file>` ([GitHub integration](https://docs.signpath.io/trusted-build-systems/github)).
- **File types:** `<pe-file>` (exe/dll, Authenticode), `<msi-file>`, `<nupkg-file>`, `<zip-file>`, nested via `path`; "deep signing" of containers and their contents ([syntax](https://docs.signpath.io/artifact-configuration/syntax)). Whether a Squirrel `Setup.exe` (which embeds the nupkg) can be re-signed after build, or how to sign inner exes before `releasify` packs them, is not documented in pages read. Forge/Squirrel signs inside the make step ([electron-winstaller source](https://raw.githubusercontent.com/electron/windows-installer/main/src/index.ts)), whereas SignPath is a submit-then-wait flow after upload; fitting these together is untested (see Unverified).
- **Certificate subject:** the Foundation provides the certificate; publisher shown would be the Foundation, not the maintainer. The pages read do not state the exact subject string (only that the Foundation must be credited ([terms](https://signpath.org/terms.html))). Treat as unverified.

## 3. Traditional certificates and cloud signing

- **Rule:** since 2023-06-01, CAs must ensure Code Signing certificate private keys are generated, stored and used in a suitable hardware crypto module (CSBR 6.2.7.4.2) ([CA/B Forum](https://cabforum.org/working-groups/code-signing/requirements/)); the fetched text does not exempt individuals. Forge's guide states the FIPS 140 Level 2 requirement ([Forge guide](https://www.electronforge.io/guides/code-signing/code-signing-windows)); DigiCert states FIPS 140-2 Level 2 or Common Criteria EAL 4+ ([DigiCert](https://www.digicert.com/signing/code-signing-certificates)). SSL.com reports a 458-day maximum validity from 2026-03-01 ([SSL.com](https://www.ssl.com/guide/code-signing-certificates/)).
- **Individual validation:** SSL.com IV is for "independent developers, open source maintainers, freelancers", government ID, no business registration; $129/yr (1 yr) down to $96.75/yr (5 yr); standard validation 3-5 days ([IV page](https://www.ssl.com/products/software-integrity/code-signing/iv/)). Sole Proprietor EV exists at $359/yr ([page](https://www.ssl.com/products/software-integrity/code-signing/ev-sole-proprietor/)). Sectigo validates "the organization or individual named in the Organization field" ([Sectigo](https://www.sectigo.com/ssl-certificates-tls/code-signing)). Certum's Open Source Code Signing certificate (EUR 69, individuals/OSS developers, includes a smartcard and reader, SimplySign cloud not included) was out of stock when fetched ([Certum](https://shop.certum.eu/open-source-code-signing.html)); a physical card is awkward in GitHub-hosted CI. Acceptance of Australian IDs/addresses by any of these CAs was not checked.
- **Cloud signing:**
  - SSL.com eSigner (FIPS 140-2 Level 3 cloud HSM): Tier 1 $15/mo, 240 signings, 1 credential; Tier 2 $63.75/mo, 1,200 signings; 30 days free for new certificates; works with GitHub Actions ([eSigner](https://www.ssl.com/products/software-integrity/signing-service/)). Alternatives on the cert page: YubiKey +$379, or your own cloud HSM with an attestation fee from $500 ([IV page](https://www.ssl.com/products/software-integrity/code-signing/iv/)). Integration via CodeSignTool, which sends only hashes ([guide](https://www.ssl.com/guide/code-signing-automation/)), and [actions-codesigner](https://github.com/SSLcom/actions-codesigner).
  - DigiCert KeyLocker: bundled with OV from $44/mo and EV from $62/mo, 12-month auto-renewing subscriptions ([DigiCert](https://www.digicert.com/signing/code-signing-certificates)). The KeyLocker GitHub integration doc URL tried returned 404, so integration details are unverified.
  - Azure Key Vault Premium / Managed HSM: per-key and hourly charges exist but the fetched [pricing page](https://azure.microsoft.com/en-us/pricing/details/key-vault/) shows no figures; whether a public OV/EV key can be issued into your own Key Vault/Managed HSM depends on the CA (SSL.com lists Azure Dedicated HSM with an attestation fee, see above). Not otherwise verified.
- **Plugging into Forge:** `@electron/windows-sign` supports `signToolPath`, `signWithParams`, `certificateFile`/`certificatePassword`, `hookFunction`/`hookModulePath`, `timestampServer`, `hashes`, `automaticallySelectCertificate`, `appDirectory`, `debug`; default signed types include .exe, .dll, .node, .sys, .msi, .msix/.appx, .cat ([README](https://raw.githubusercontent.com/electron/windows-sign/main/README.md)). electron-winstaller describes `windowsSign` as supporting "cloud-hosted EV certificates, custom sign pipelines, and per-file overrides" ([README](https://raw.githubusercontent.com/electron/windows-installer/main/README.md)). A vendor CLI (e.g. CodeSignTool) can be wrapped in a `hookModulePath` function (inference from the option list; not shown in the README text read).

## 4. SmartScreen and Smart App Control

- **SmartScreen signals:** publisher reputation (is it signed, by whom) and file hash reputation. Unsigned: "Windows protected your PC", user must choose "Run anyway"; enterprise policy can prevent continuing; reputation restarts for every new version and cannot carry over. OV/EV: still a warning until reputation accumulates, publisher name shown; self-signed behaves like unsigned ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)).
- **EV:** "EV certificates no longer bypass SmartScreen... Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified." (same page). SSL.com's Sole Proprietor EV FAQ agrees ("since 2024... all certificates now accumulate reputation"), while its OV page still mentions an EV "immediate SmartScreen reputation benefit" ([EV SP](https://www.ssl.com/products/software-integrity/code-signing/ev-sole-proprietor/), [OV](https://www.ssl.com/products/software-integrity/code-signing/ov/)). Electron's docs still say Microsoft "requires" an EV certificate and that older types leave the app treated as unsigned ([Electron](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/code-signing.md)); this conflicts with Microsoft's table above, which lists OV/EV as one row. Microsoft's page is more recent (updated 2026-08-17).
- **Reputation build-up:** "can take several weeks and hundreds of clean installs from a wide audience"; no mechanism to pre-submit for consumer endpoints; Store-distributed apps never get the warning ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). The Artifact Signing FAQ points to Microsoft Security Intelligence for continued prompts on signed files ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)).
- **SmartScreen scope:** checks downloaded files against known-bad and "well known and downloaded frequently" lists and warns if unknown; it does not cover network shares/UNC ([SmartScreen overview](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/)).
- **MSI vs exe:** no fetched Microsoft page distinguishes SmartScreen behaviour for MSI and exe; unverified.
- **Smart App Control (Windows 11):** "Malware, Potentially Unwanted Apps (PUA), and unknown, unsigned code are blocked by default." In enforcement mode "Apps cannot be run unless they are recognized by Microsoft's app intelligence services, or they are signed with a trusted certificate"; if the intelligence service cannot predict, a file signed by a CA in the Trusted Root Program is allowed ([Learn](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview)). It only turns on after a clean install of a supporting Windows 11 build, "only enabled in certain regions", and is turned off automatically for users it judges developer-like (same page). The SmartScreen doc adds: "Smart App Control will block execution of unsigned files unless the file has a positive reputation. Smart App Control signature checks apply to all executable files, not just those downloaded from the Internet." ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). Consumer FAQ: an app without a valid signature that the service cannot confidently predict is blocked as "untrusted"; SAC can be re-enabled without a clean install after recent updates ([Support](https://support.microsoft.com/en-us/topic/what-is-smart-app-control-285ea03d-fa88-4d56-882e-6698afdb7003)), which conflicts with the Learn page's clean-install statement.
- **Net effect of unsigned, precisely:** with SAC off (default for many existing installs and for developer-like users), the user sees the SmartScreen dialog and can "Run anyway". With SAC in enforcement mode, an unsigned installer or binary without positive cloud reputation is blocked, and the docs read do not offer a per-file "Run anyway" bypass. A brand-new unsigned release has no reputation, so blocking is the documented expectation (inference from the two Microsoft statements; not tested).

## 5. Electron tooling

- **Where signing happens:** "On Windows, Electron apps are signed on the installer level at the Make step"; all tools use `@electron/windows-sign` exposed as `windowsSign` in Forge, Packager, electron-winstaller and electron-wix-msi ([Forge guide](https://www.electronforge.io/guides/code-signing/code-signing-windows), [Electron](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/code-signing.md)). Packager: "If present, signs Windows binary files" ([Options](https://electron.github.io/packager/main/interfaces/Options.html)).
- **maker-squirrel config:** Forge shows `certificateFile`/`certificatePassword` (legacy; `.pfx` which hardware-key rules now largely preclude) or `windowsSign` for custom pipelines ([Forge guide](https://www.electronforge.io/guides/code-signing/code-signing-windows), [electron-winstaller README](https://raw.githubusercontent.com/electron/windows-installer/main/README.md)). maker-wix: `windowsSign` supported by electron-wix-msi ([Electron](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/code-signing.md)).
- **What gets signed for Squirrel:** Squirrel docs: it "signs all of your application's executables as well as the final generated Setup.exe" ([application-signing](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/application-signing.md)). electron-winstaller passes `--signWithParams` (or `windows-sign`) to Squirrel's `--releasify`, so Squirrel signs Setup.exe, Setup.msi, Update.exe and package contents, rather than electron-winstaller signing files itself ([source](https://raw.githubusercontent.com/electron/windows-installer/main/src/index.ts)). Setting `packagerConfig.windowsSign` additionally signs the packaged app's binaries (exe, dll, .node) before packing, as in Forge's example ([Forge guide](https://www.electronforge.io/guides/code-signing/code-signing-windows)). The `.nupkg` itself is not an Authenticode-signed file in these docs; its integrity check in updates is a SHA1 in `RELEASES` ([update-process](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/update-process.md)).
- **Bundled `node.exe` (private, in resources):** the Node release process signs Windows binaries with a DigiCert certificate held by the OpenJS Foundation; a 2023 issue discusses renewing the one obtained in 2020 that expired 2023-12-18 ([nodejs/build#3491](https://github.com/nodejs/build/issues/3491)). I did not find a Node doc stating that the current official `node.exe` is signed or by which identity, so the claim should be checked on the actual binary (`signtool verify /pa /v node.exe`) (see Unverified). If it is validly signed, re-signing is not required for SmartScreen/SAC publisher checks by this reading; re-signing would replace the OpenJS signature unless appended: SignTool `/as` appends a signature ([SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)). `@electron/windows-sign` signs `.exe` by default, so it would try to sign `node.exe` if it is under the signed directory; excluding it needs `files` or hook handling (not tested; README default type list only was read).
- **dugite git binaries:** the dugite README fetched does not say which Windows Git binaries are bundled or whether they are signed ([dugite](https://raw.githubusercontent.com/desktop/dugite/main/README.md)). Under SAC, SAC "signature checks apply to all executable files" ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)), so unsigned unpacked `git.exe` helpers are exposed unless signed or recognised; signing them would require adding them to the signing file list. Their current signature status is unverified.

## 6. Do unsigned Squirrel/MSI installs still auto-update?

- Electron's `autoUpdater` docs state a signing requirement for macOS (Squirrel.Mac) but no Windows equivalent; the Windows section only describes format detection ([auto-updater](https://raw.githubusercontent.com/electron/electron/main/docs/api/auto-updater.md)). Electron's updates tutorial lists signing as mandatory for update.electronjs.org on macOS only (and MSIX) ([updates](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/updates.md)).
- Squirrel.Windows' update process: compares `RELEASES`, downloads full/delta nupkgs, verifies SHA1 from `RELEASES`, extracts into `app-<ver>` under `%LocalAppData%`; no signature verification is described ([update-process](https://raw.githubusercontent.com/Squirrel/Squirrel.Windows/develop/docs/using/update-process.md)). So documentation implies unsigned updates are mechanically possible; not tested.
- **Update path and SmartScreen/SAC:** the Squirrel update flow is not described as setting a download-origin marker and no fetched Microsoft page says whether SmartScreen evaluates files extracted by Squirrel (unverified). SAC, by contrast, checks all executable files, not only downloaded ones ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)), so under SAC enforcement an unsigned updated `app-<ver>\*.exe` and DLLs would be evaluated again, each new version starting with no hash reputation ("unsigned files must build reputation anew with every update", same page). MSI installers (electron-wix-msi) have no Electron auto-update path (see [windows-installer.md](./windows-installer.md)).
